# GridProof threat model

**Service-readiness extension (2026-10-19).** The new controller simulation masks future outcomes before solving, requires the zero-PV import envelope, and freezes previously executed controls during event replanning. Evidence includes the original service request and ordered parent/child history; independent checks reject a rewritten executed prefix even after the parent is rehashed. This verifies self-consistency, not real execution, telemetry authenticity or that a parent was externally committed before the event. An attacker controlling an entire self-consistent history still needs an independent prior digest/receipt or signed device telemetry to be caught as a historical fabrication. Current source, local-chain and meter-truth limitations below remain.

Service promises assume declared fixed loads, continued connection through the promised time, functioning chargers/battery and the modeled efficiency/capacity. Unknown departure before that time, additional base load and hardware outages are not guaranteed. A rejected revised request must not silently inherit a green promise from the old plan; the UI labels it as the previous plan and disables plan/evidence exports until a new accepted plan is computed. The disconnect tool assesses a simulated outcome and sends no hardware command.

GridProof handles public grid snapshots, a hypothetical campus schedule, deterministic report bytes, and a registry commitment. The local demonstration is a development environment controlled by the operator. It is not a decentralized deployment or a regulatory certification system.

| Boundary / attack | Implemented defense | Residual limitation |
|---|---|---|
| Evidence JSON changed after commitment | Backend hashes the specified deterministic canonical bytes with SHA256; verifier compares this digest with the active registry record and its registration event. | Hashes establish integrity of the chosen bytes; a false input can be hashed honestly. Independent replay and source inspection remain necessary. |
| Same report scope presented as a different scenario or model | Contract computes `keccak256(abi.encode(siteHash,uint64 fromUtc,uint64 toUtc,categoryHash))`. Model/scenario IDs and report digest are excluded from the uniqueness key. | Uniqueness covers exact tuples only. Overlapping intervals, alternate site identifiers/categories, and another registry can evade a broader real-world double-claim policy. |
| Claim revoked by an unrelated address | Only the recorded submitter may revoke or replace; nonzero reason digest is required. Replacement requires prior revocation and emits linked immutable events. | Loss or compromise of the submitter account affects availability/authorization. No administrator rescue is implemented. |
| History silently overwritten | Separate numbered records retain previous digest, submitter and creation time; revoke/replace updates explicit status and relation fields. Registration/revocation/replacement events remain in chain history. | A local node can be reset. Runtime receipts are evidence from that run, not durable public-chain finality. |
| Wrong chain, changed contract, reset node, fabricated transaction, stale event | Bridge checks chain31337, deployment receipt against captured block hash/number and the canonical block, deployed bytecode SHA256, current active record, matching registration event, successful transaction receipt and canonical registration block. Captured deployment-block comparison catches deterministic address/transaction-hash reuse after a reset. | The configured local RPC is trusted to answer honestly. A malicious RPC can invent a consistent chain; an independent public deployment/RPC would be required for stronger assurance. |
| RPC outage, missing event, cancelled/reverted transaction | Verification returns `UNVERIFIABLE` with a concrete error; no cached receipt alone can produce `VERIFIED`. Digest mismatch and revocation are separate states. | A failed verification may reflect service availability rather than malicious evidence. |
| False source, source revisions, simulator bug, forecast leakage | Source hashes/provenance, numerical constraints, held-out chronological checks and disclosed decision-time limitations are required throughout the application. | Registry does not inspect physical sensors, licenses, scientific correctness, site ownership or data availability. |
| Site squatting / front running | Existing exact active scope cannot be overwritten; original submitter alone can manage its lifecycle. | Initial registration is permissionless. Anyone knowing the site hash may occupy the scope first. Production needs audited site-identity authorization. |
| Private data and credentials | Local bridge uses unlocked Hardhat development accounts without storing secret keys; accepts only loopback HTTP RPC and does not support public networks. Bulk data, deployments and runtime receipts are ignored from source control. | Site hashes can be guessed from low-entropy site names. Reports may contain operationally sensitive parameters. Hashing is not encryption. |
| Unintended onchain writes | Health and verify are read-only. Attestation is a deliberate API/UI action; startup deploys only to the local node and does not register evidence. | Local demo API is a trusted workstation tool. Authentication, authorization, robust public rate limits and production transaction signing are required before exposing write endpoints. |
| Denial of service / malformed input | Scope/digest/timestamp validation, whole-second UTC, bridge input128KiB limit, RPC timeouts and no shell-interpolated JSON. | Development infrastructure is not hardened for untrusted public workloads. |

The contract has no external calls, token minting, transfers, fees, delegate calls, upgrade mechanism, or owner powers. This substantially limits its attack surface but is not a security audit. Solidity tests cover replay, changed model/scenario, unauthorized lifecycle changes, zero digests, invalid intervals, tampering and linked history. Bridge tests cover wrong network, unavailable RPC, stale deployment and missing events.

## Car-park control records (October 19)

Covered: rewriting recorded charging or results after the fact (physics checks and decision replay), a consistent rewrite of a departure or session, or omitting servable sessions from the day (source correspondence against the pinned raw session file, in both directions), forged grid values (pinned NESO/ERA5 reconstruction), and ready-by targets edited after the fact for the replayable policies (decision replay mismatch). Not covered: a producer who fabricates the whole day before hashing *and* controls the raw-file digest; ready-by targets that came from a different model (only the model fingerprint is committed); LP decisions (constraint-checked, not re-solved); physical execution; when the record was first written unless a counterparty-witnessed registry entry exists. Session-derived records fall under CC BY-NC-SA 4.0 and should not be published without consulting the dataset contacts.
